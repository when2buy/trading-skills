# How the loop evolved (case history)

Distilled from ~6 weeks running an LLM-serving cluster with a small team of engineers and many
agents. Details are generalised: no machine names, addresses, or customer data. Read it to see
that each rule was earned by a specific failure, not invented.

| Stage | What happened | Rule it left behind |
|---|---|---|
| 0. Mirror + self-audit | Research notes were mirrored into git. The first job was not adding content but **making an agent audit the knowledge base by its own rules**: it found five self-contradictions (a documented figure 2x off the measured one; three claimed gains smaller than baseline drift; a headline speedup with no source anywhere) and listed seven claims it had checked and found sound, to avoid criticism for its own sake. | **Numbers need a source; a gain must exceed noise.** |
| 1. Read-only survey overturns the plan | A plan was written, then a 30-minute read-only pass over the live machines overturned four items (the fault was in the front-door admission layer, not the workers; an alleged night-time slowdown had no evidence; monitoring had been down for weeks; utilisation was near zero). | **Define the problem first; survey the live system before planning.** |
| 2. One hypothesis per version | A front-end went through 18 versions in four days, each testing exactly one hypothesis, each with a rollback command and a post-deploy check. Rejected designs stayed in the repo next to adopted ones. | **Change one variable at a time; keep negative results.** |
| 3. Same-bytes comparison + standard cases | A model emitted garbage on certain inputs; only replaying the *same request bytes* against a reference deployment localised the fault to the engine layer. A customer-path check found one in six billing fields correct while every HTTP status was 200. | **Before/after on identical bytes (hash-checked); 200 is not a pass; a standard case set.** |
| 4. Two repos, two jobs | Knowledge repo holds *why* (plans, designs, SOPs, evidence); ops repo holds *how* (versions, patches, scripts, rollback). | **Split decisions from execution; cross-link.** |
| 5. The yardstick itself is iterated | The original per-step timing metric varied 4-9% between identical runs - bigger than most optimisations. Switching to a steady-state-only measure and locking clocks cut noise to under 2.4%; a 2% threshold was set; quality gates (paired tests) were added the same day. | **Measure the yardstick's noise before measuring changes.** |
| 6. Rules written into AGENTS.md | Two incidents of someone replacing machines without telling anyone, and a `pkill -f` that killed the service and the agent itself. | **Hard-rules table; every rule names its incident.** |
| 7. Parallel agents + errata | One day: 12 parallel investigation threads + one integration review -> recommended config the same day, rollout the next. Sub-agents are sometimes wrong, so records carry an "errata" section: a cross-machine "regression" turned out to be that machine being 6% slower. | **Lead re-verifies on raw data; cross-machine claims re-run on one machine.** |
| 8. Reliability substrate | Admission control, watchdogs, stable-version records per object, and a drift check between live and git, built in a day. | **After any change, sync config / architecture page / status.** |
| 9. One task table + delegation | Five parallel plans each had their own IDs and nobody knew what to do next. Collapsed to roadmap -> orthogonal workstreams -> one task table -> milestone checkboxes + one open-questions page. Eight read-only tasks delegated with guardrails written first; the agent fixed six doc/reality mismatches and, on finding a public exposure, **stopped and reported per the circuit breaker**. | **Guardrails before delegation; one task table; canary -> solid benchmark -> human approval -> production.** |
| 10. Agents run research rounds | Each round has its own directory and a `verify.py` that checks evidence hashes; ~100 commits in two days. About 13% of evidence files were failures, retractions, or corrections. A round's conclusion was scoped ("holds in the isolated pool, not extrapolated"), which defined the next round's question. | **Every round independently re-checkable; scope every conclusion; last round's result sets next round's question.** |
| 11. Data-driven single-point optimisation | Fit real traffic first (cost dominated by *cached* length) -> reproduce production on a spare machine (artifacts hash-checked) -> match production within 15% -> per-stage breakdown -> found a redundant per-request pre-step -> a one-line change halved latency on long cached prompts with identical output -> risk review + realistic stability test -> hand the verdict to the owner. | This is the seven-step round in `SKILL.md`. |

**Pattern:** every speed-up came from turning a judgment that lived in someone's head into
something in the repo - a rule, a yardstick, a template, a verification script.
